## TL;DR

- 講者以同一支颱風假校園短劇，比較租用 Colab 執行 MiniMax H3，與透過 Kie.ai 呼叫 Seedance 2.5 兩條路線；操作入口統一在 Agent 對話。
- 真正的前置工作是劇本、角色與場景資產、配音、分鏡試映及各鏡頭首幀（First Frame）。先審這些產物，可降低昂貴的影片重生次數。
- 本次講者回報 H3 由本機與 Colab 分工，26 個片段成功、耗時 771 秒，Colab 消耗約 1.43 單元；這些數字沒有涵蓋整場兩個多小時的前置與審核。
- 講者最後回報約 90 秒 Seedance 2.5 成片花費新台幣 1,070 元，實際偏好讓 H3 處理一般鏡頭，複雜動作改用 Seedance 2.0 Mini。
- 可先做一段短對話試點，記錄前置、生成、重試及人工審核成本，再決定是否擴大。此項試點設計是本筆記建議，本次未部署任何影片工作流程。

## 摘要（Summary）

這場直播示範一套由 Agent 串接的短片製作工作流程（Workflow）：人提供題材與受眾經驗，Agent 協作劇本、整理角色資產、製作配音試映、產生首幀，再把各鏡頭送往本機、Colab 或影片 API，回收片段後自動組接與加字幕。範例是一支約一分半的校園颱風假喜劇。

影片值得保存的內容包含完整前置流程、同題材兩版比較，以及實際漏送聲音資產所暴露的返工成本。講者將 Seedance 2.5 稱為品質「天花板」，這是個人評價；本筆記不將它外推為跨模型排行榜或普遍適用的採購結論。

## 關鍵洞察（Key Insights）

- **先降低重做的單位成本。** 劇本與配音試映階段即可發現節奏及發音問題；等影片送出才發現漏音檔，會讓同一個錯誤擴散到多個付費鏡頭。
- **角色一致性依賴可重用資產。** 全身、近照、轉面與表情參考，加上場景不同視角與角色聲音，比每次重新描述外觀更容易管理。
- **統一對話入口仍需要底層工具。** 講者不手動開 ComfyUI 介面或剪輯軟體，但背景仍用 ComfyUI、腳本及 API 執行生成與後製。
- **算力加速與創作時間要分開。** 771 秒生成結果不包含先前的劇本討論、數十張首幀候選、發音修改和後續粗剪。
- **影片生成可視為有驗收條件的長任務。** 角色、聲音、鏡頭設定和修改要求必須跨步驟保留，可對照 [[2026-04-07-AI-AGENT-PAINFUL-LESSONS-TUTORIALS-TO-REALITY|長任務的上下文與重述問題]]。

### 2. 先寫出值得看的內容

[00:26:49](https://www.youtube.com/watch?v=lneWkkZrg70&t=1609s) 起介紹編劇技能（Drama Skill）。它把題材發展成劇本、分鏡表及生成前的讀本試映。講者認為，當生成技術逐漸普及，領域經驗、受眾理解與故事品質會更有區別。

範例提示的資訊結構可整理為：

1. **情境與受眾**：台灣教學現場，老師與學生。
2. **主題與片長**：颱風假，約 60–90 秒。
3. **已有觀察**：老師擔心進度、提前加派作業，學生持續關注放假消息。
4. **補充素材**：請 Agent 搜尋其他具有共鳴的情節，再提交腳本供審閱。
5. **內容篩選**：避開不適合學生的低俗笑點，並讓反轉能回扣前面鋪陳。

直播採用的反轉之一，是老師先派大量作業，最後發現自己要批改更多。此處整理提示的結構，未將字幕重寫版冒充為逐字提示詞。

### 3. 把人物、空間與聲音都做成資產

[00:42:34](https://www.youtube.com/watch?v=lneWkkZrg70&t=2554s) 起的角色資產（Character Assets）包括：

| 資產 | 內容 | 可解決的問題 |
|------|------|------|
| 定裝參考 | 全身、正面近照、四分之三近照 | 穩定人物外觀與服裝 |
| 轉面參考 | 正面、側面、背面等角度 | 減少換鏡位後人物變形 |
| 表情參考 | 該角色會使用的表情 | 維持演出設定 |
| 場景參考 | 同一教室前看後、後看前 | 維持空間方向與配置 |
| 聲音參考 | 角色對應的錄音或合成聲音 | 維持角色聲線 |

講者把不同系列的資產分資料夾存於本機，需要生成時再傳到執行端。這是講者採用的參考素材方法，不代表所有人物、角度或模型都能保證完全一致。

### 5. 先確認聲音，再依鏡頭生成影片

[01:24:11](https://www.youtube.com/watch?v=lneWkkZrg70&t=5051s) 的重點是讓對白與口型（Lip Sync）一起規劃。講者希望先完成聲音，再讓影片生成配合聲音；若成片後才任意替換對白，會增加口型不同步的修正工作。

講者也區分一般發音正確與台灣腔。此案例中前者修正後，後續仍出現其他字音問題，顯示不同階段與不同模型的聲音都需要再聽一次。

### 6. 平行生成有助縮短等待，仍要確認比較條件

### 7. 漏送角色參考音：最具體的失敗案例

在 [01:50:30](https://www.youtube.com/watch?v=lneWkkZrg70&t=6630s)，講者發現 Seedance 版本未送角色參考音。當時工作已提交，講者回報若重做 14 個有台詞鏡頭、共 62 秒，需要約 3,900 點，因此決定保留這次缺陷。

他隨即要求修改工作流程，讓已有角色參考音時必須附上，沒有才自行生成。這是直播中的修改要求；本次未追蹤該邏輯是否已完整寫入與實測。

> [!tip] 本筆記建議：把資產完整性變成提交條件

### 10. 品質比較與最後的混搭策略

[02:12:32](https://www.youtube.com/watch?v=lneWkkZrg70&t=7952s) 開始播放兩版對照。講者認為 Seedance 2.5 的動作、表情與提示詞遵循較好；一般對話的靜態鏡頭差距較小。兩版仍需修正，且 Seedance 版本缺少原定角色參考音。

[02:18:14](https://www.youtube.com/watch?v=lneWkkZrg70&t=8294s) 之後的策略是按鏡頭混搭（Hybrid Workflow）：一般或靜態片段用本機／Colab H3，跑步、誇張動作、武打與複雜表演改用 Seedance 2.0 Mini，再交給 Agent 組接。**Mini 是講者既有使用經驗與最後建議，這場完整兩版對照的付費模型是 Seedance 2.5。**

### 11. 作者公開 repo 與直播私有專案有差異

2026-10-25 靜態查閱時，作者 [Colab README](https://github.com/mathruffian-dot/shanshiba-workflow-colab#readme) 將雲端 GPU 生成與本機素材管理分開；[本機版 README](https://github.com/mathruffian-dot/shanshiba-workflow-32gvram-64gram#readme) 則說明公開版調整為本機模型，未附本人照片、克隆聲音、金鑰或角色定裝素材。因此拿到公開 repo 不等於取得直播中的完整個人素材與設定。

兩份 README 的一般範本寫 16:9，直播編劇流程則提到預設 9:16；應明確設定個別專案比例，避免混用。直播中也發現配音試映及 16 宮格流程尚未全部公開，並要求補上，不能將直播中口頭宣布更新等同於目前 repo 所有流程都通過執行驗證。

> [!warning] 作者 repo 的授權提醒
> [Colab README](https://github.com/mathruffian-dot/shanshiba-workflow-colab#readme) 列出模型用途與地區限制，並特別提醒所述 Colab 機房位置與 MiniMax H3 排除地區的衝突。講者在 01:54 左右也承認跨區租機使用的判定不確定。本文記錄此未解問題，沒有查核全部上游授權條文，也不據此判定任何使用情境已獲允許。

## 我的心得（My Takeaways）

以下是本筆記的分析與建議：

1. **最值得移植的是驗收順序。** 先驗劇本、聲音與首幀，再生成影片，可把錯誤留在便宜的階段處理，和 [[2026-06-30-AI-DLC-CLAUDE-CODE-END-OF-VIBE-CODING-VS-OPENSPEC-SUPERPOWERS|分階段驗收的開發流程]] 有共同原則。
2. **Agent 負責協調，資產清單負責完整性。** 這次漏音事件說明，只靠對話記憶仍會漏掉必需輸入；可用明確清單和提交條件補強。
3. **先證明適合自己的鏡頭，再談整體加速。** 可挑相同的靜態對話與複雜動作各一鏡，比較重試次數、可用率、耗時和可接受成本，再決定混搭比例。
4. **建立可停止、可續跑的工作循環。** 應保存片段、鏡頭狀態及修改清單，讓生成與審核有明確完成條件，可對照 [[2026-06-07-LOOP-ENGINEERING-THREE-SOURCE-EXPERT-SYNTHESIS|迴圈工程的驗證與停止條件]]。

### 分析型追問（Socratic Follow-up）

- **澄清**：「品質比較好」指動作、角色一致性、發音、口型還是整體敘事？每一項如何評分？
- **假設**：若沒有現成角色與聲音資產，首次製作的總成本是否仍符合影片的低成本印象？
- **證據**：若重做相同 26 鏡三次，771 秒及 1.43 單元的波動會多大？應如何設計單機基準？
- **觀點**：若由剪輯師評估，哪些步驟直接使用剪輯工具會更快、更容易檢查？
- **後果**：若一年持續產片，素材版本、模型改版與參考音相容性會增加多少維護工作？

### 方案批判三問（Critical Evaluation）

1. **最大的風險是什麼？** 缺少必要素材卻一次提交大量付費鏡頭，導致不可回收的重做支出；直播漏音就是具體案例。
2. **什麼情況下會失敗？** 公開 repo 缺少私人資產、環境無法重建、GPU 資源不足、參考素材不相容，或驗收要求超出模型能力時。這些是待測前提，未在本次逐一實驗。
3. **有沒有更好的替代方案？** 純 API 減少環境維護，但可能提高重試費；分鏡圖加真人旁白能避開部分口型問題，但動態表演較少；人工剪輯提供直接控制，適合自動流程難處理的細節。應依交付需求選擇。

## 六頂思考帽回饋（Six Thinking Hats Feedback）

### 藍帽：問題與範圍

要決定的是如何完成一支可交付短片，以及哪些鏡頭值得付較高生成費。本文範圍是直播工作流程與講者回報，執行環境與成片評分未獨立驗證。

### 白帽：事實與未知資訊

已取得影片元資訊、完整字幕與作者 repo README。字幕具體記錄漏音、26 個成功片段、771 秒及 1.43 單元；缺少原始工作記錄、完整帳單、評分資料與同條件重複試驗。

### 紅帽：直覺與讀者反應

讀者可能被「對話就能做片」吸引，也可能被長時間前置與繁多名詞壓倒。漏音後不願付費重做的片段，尤其容易讓人感受到成本壓力。

### 黃帽：價值與可保留內容

保留可重用資產、先試映再生成、按鏡選模型、集中修片及關機回收的做法。這些原則在工具更換後仍有參考價值。

### 黑帽：風險與限制

單場示範的硬體、素材及聲音輸入不完全對等；品質與「最便宜」主要是講者判斷。直播私有專案、公開 repo 與即時服務的差異，也會影響重現。

### 綠帽：替代方案與新應用

可先用配音分鏡做需求驗收，再挑少數關鍵鏡頭升級為動態影片；也可把每鏡的模型、資產、成本與修改原因存成清單，方便局部重做。這些是本筆記提出的延伸方案。

### 藍帽：修改項目與下一步

- 保留明確數字與時間點，同時標示成本及計時的涵蓋範圍。
- 將參考音完整性及同輸入比較列為試點必查項目。
