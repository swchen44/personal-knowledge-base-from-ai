語言適用性

「可以用」的三個層次。

流程、語法與驗證環境各自有不同範圍。對 C 開發者，最有價值的是可重現的工作方法；具體規則仍應以 C、SDK 與 kernel 規範為準。

pstack 的能力用於 C研究結論
研究、設計、除錯、審查可直接沿用流程讀 repo、追根因、小幅修改、依證據交付，沒有要求專案用 TypeScript。[1]
型別與狀態建模按 C 能力調整可用 struct、enum、opaque handle 表達合約；C 的型別檢查無法自動保證 lifetime、ownership 或所有非法狀態。[2]
TypeScript 最佳實務不套用語法規則unknown、satisfies、branded intersection 等是 TS 專屬。該 skill 明確只匹配 .ts / .tsx。[3]
行為與形式驗證生成接上專案工具兩類 skill 都宣稱跨語言，但要找出真實命令、建立 harness 並執行。沒跑過的驗證 skill 仍是草稿。[4][5]
FreeRTOS／Linux 硬體驗證需要領域適配本次原始版 skills/agents 關鍵字搜尋未見對應的專屬操作說明。這不代表通用 agent 無法協助，也不代表已具備板端驗收能力。

表內對 C 的轉用方式是工程判斷。pstack 支援腳本使用的 JavaScript／TypeScript／Bun，不會限制被開發專案的語言。

先從可隔離的 C 邏輯開始。

  • 檢查邊界、整數運算、指標與資源生命期。
  • 高風險小模組可評估 CBMC，明示假設和界限。[10]

最合適的起點
讓一個既有 bug 可重現，保留修改前失敗、修改後通過的輸出。原版 TDD skill 也允許在測試成本不合理時採用最近的可執行驗證。[6]

讓 task 與 ISR 的合約可見。

pstack 可協助分析 queue、semaphore、notification、timeout 和 buffer ownership。實際調度、interrupt 與硬體行為仍要由目標環境提供證據。

  • 先辨識 task context 與 ISR context，依 port 核對 API 與優先序。
  • 把 toolchain、FreeRTOSConfig、linker script 與 SDK 版本寫進專案規範。
  • 接上 build、燒錄／重設、UART log 或 debug harness；無板端存取時明示未驗證。[11]

以 kernel 的規範與工具驗證。

pstack 可協助追蹤 probe/remove、資源清理、IRQ、workqueue 和共享資料。原始碼審查之外，仍須測試實際 kernel 與裝置介面。

  • 鎖定 kernel commit、.config、architecture 與 compiler。
  • 局部邏輯用 KUnit，使用者可見介面依情境用 kselftest。

設計模型

TLA+：事件順序對不對？

適合探索小型並行狀態模型。例如 queue 的生產／消費與 reset 是否可能造成遺失或錯誤 ownership。這是候選性質；原版要求模型步驟對應到 code，通過只涵蓋該模型與假設。[4]

C 程式碼

CBMC：界限內會不會出錯？

可檢查 C 的越界、指標使用、部分 undefined behavior 與 assertions。FreeRTOS 官方 repo 也有 CBMC proofs，但你的應用程式仍需自己的 harness；此工具不由 pstack 內附。[10][11]

嵌入式適配

保留硬體需要的理由。

pstack 有鮮明的簡化與刪減偏好。以下是對 C／kernel 的採用判斷，應寫成專案規範，讓 agent 知道哪些介面與合約有工程用途。

「信任內部型別」需要前提。

原則原文主張內部不重複驗證。C 的指標、長度、異步資料與 ownership 未必由型別保證；應依故障模型保留必要 assertions、邊界與同步。[8]

單一 caller，不足以判定 wrapper 多餘。

HAL、MMIO accessor 或測試替身介面可能封裝 ordering、架構差異與硬體限制。Linux 的 __iomem、readl/writel 有明確合約。[8][15]

errata 與 ordering 的註解要能留下。

no-comments 的預設積極刪註解，但原版 reviewer 明列 vendor、platform、protocol、public API contract 等例外。硬體限制應連到 datasheet／errata，保留不可由程式自明的原因。[9]

精簡程式，要一起保留同步語意。

不可只憑行數刪掉 barriers、critical section 或 ownership transfer。Linux 官方也明確說明，volatile 無法取代並行保護；firmware 則按架構和 SDK 的 MMIO 規範處理。[15][16]

採用建議

先接好一條可驗證的路。

建議把 pstack 當作流程底座，逐步補專案知識。從單一可重現問題開始，較容易判斷它對你的團隊是否有幫助。

1

界定開發合約

記錄 CPU、compiler、SDK、RTOS／kernel 版本、build 命令、記憶體限制、ISR 與同步規範。寫進 repo 的 agent 規範。

2

接上驗證入口

沿用既有 build、測試、板端操作與 log。再請驗證生成 skill 整理可重跑方法；先執行成功，才列為可用。

3

試跑一個真實 bug

選 queue、timeout、parser 或 driver cleanup 的已知問題，保留失敗與修正後證據。依實際結果決定擴大範圍。
